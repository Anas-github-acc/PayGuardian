## 2. Logic Chain

1. **Elimination of Mock Fixtures**:
   - In accordance with the project integrity mandate, `DEFAULT_APPROVALS` (144 lines in `apps/web/components/approvals/types.ts`) and `DEFAULT_TRACES` (494 lines in `apps/web/components/traces/types.ts`) were completely deleted.
   - All references to these mock datasets in components (`ApprovalsInbox.tsx`, `PaymentTraceView.tsx`) were replaced with direct queries to backend hooks (`useApprovals`, `usePaymentTrace`).
2. **Enforcement of R3 (Zero Optimistic Updates for Approvals)**:
   - In `apps/web/components/approvals/ApprovalsInbox.tsx`, `handleApprove` and `handleReject` were restructured:
     - The item remains in the UI and pending count remains unchanged while the mutation is in-flight (`isMutating` state tracks active IDs).
     - Only when `await apiClient.approvals.approve(...)` or `reject(...)` succeeds (HTTP 200 confirmed by the server) does the local list filter out the approved/rejected item and the pending count decrements.
     - If the network call or server returns an error, the error is displayed to the user and the item remains in the list.
3. **Server-Driven Permissions (`allowedActions`)**:
   - In `ApprovalCard.tsx` and `ApprovalDetailDrawer.tsx`, client-side recalculation of `isHardLimitExceeded` was eliminated.
   - The UI strictly examines `approval.allowedActions?.includes("approve")` and `approval.allowedActions?.includes("reject")` to enable or disable the corresponding buttons.
   - `mapApprovalDtoToItem` in `apps/web/lib/api/mappers/approvals.ts` inspects `dto.allowed_actions` / `dto.allowedActions` first, or falls back to backend state mapping.
4. **Enforcement of R2 ("Never Invent Data") & GAP-TRC-01 in Payment Trace**:
   - Fastify Gateway trace endpoints provide authentic `{ action, agent, mandateChain, rootMandate }` and `{ reservation }` data.
   - Mandate chains are accurately transformed into hierarchical `TraceAuthNode` trees with integer minor units for `allocatedMinor`, `spentMinor`, `reservedMinor`, and `availableMinor`.
   - Because 5-stage latency metrics and 5-point checklist records are not generated by the backend, the mapper returns `stages: []` and `checklist: []`.
   - In `LifecycleTimeline.tsx` and `VerificationChecklist.tsx`, empty states render explicit "Unavailable" containers explaining that the backend telemetry is not yet implemented, tagged with `GAP-TRC-01`.
   - `docs/gaps.md` was updated to document `GAP-TRC-01` explaining the missing telemetry and UI unavailable states.
5. **Layout-Matched UI States**:
   - Both Screen 3 (`ApprovalsInbox.tsx`) and Screen 4 (`PaymentTraceView.tsx`) implement matching loading skeletons (matching header metrics and card layouts), error states with retry buttons, and empty states ("No pending approvals", "No payment trace selected").
6. **Isolated Contract Testing**:
   - To respect Next.js App Router tsconfig `"jsx": "preserve"` setting, `apps/web/components/approvals/__tests__/approvals-and-traces.test.ts` exercises contract logic, allowedActions button gating, mandate hierarchy traversal, and R2 zero-fabrication assertions purely in TypeScript.

## 3. Caveats

1. **Gateway Telemetry Coverage (`GAP-TRC-01`)**:
   - The Fastify Gateway does not currently record microsecond stage latencies (policy check, sandbox eval, ledger reservation, rail submit, settlement) or per-trace cryptographic validation checklist records. Per R2, these tabs display an explicit "Unavailable" status rather than synthetic data.
2. **Dynamic Trace Selection**:
   - When Screen 4 loads without a pre-selected `traceId`, it displays an informative empty state prompting the user to select an action trace.
